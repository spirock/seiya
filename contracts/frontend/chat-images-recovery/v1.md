# Recuperación del registro chat/imagen v1

Complemento al flujo existente, sin cambiar API, formato del historial o assets
congelados. Un pending local es una referencia, nunca autorización ni prueba de
que la imagen se haya generado.

- El guard de borrado se consulta dentro del handler compartido ANTES de sus
  operaciones open/list/cancel/forget. Un listener posterior no es suficiente.
- Solo una lista validada del broker de la conversación activa puede acreditar
  que existe un trabajo con el request_id pendiente. Un fallo/lista vacía no
  autoriza borrar la referencia ni reejecutar nada.
- Un botón explícito confirma el registro observado: guarda la eliminación del
  pending, limpia solo el mismo texto del compositor y conserva cualquier otro
  borrador. Si falla localStorage se revierte el cambio en memoria/editor.
- Confirmar recuperación no hace POST de chat/submit, no vuelve a inferir y no
  declara PNG terminado. Estado/PNG siguen en panel, solo completed permite verlo.
- Respuestas inválidas o IDs/fases incompatibles conservan el pending. El ACK
  debe ser un objeto de trabajo, no false/null/string con coerciones ambiguas.
- Cambiar conversación, refrescar, respuestas tardías o un polling fallido no
  confirman un trabajo distinto. No almacenar cookies/capabilities/URLs Blob.

Alternativa descartada: quitar el pending al cargar/reintentar o basarse en una
lista vacía. Podría duplicar una generación de resultado incierto. Rollback:
retirar hook/complemento y volver al reenvío manual del mismo ID existente;
no borrar historial, jobs, marcadores o configuraciones.
